# GPU DSL 四项主张的控制实验设计

## 从研究问题、推理链和缺失证据，到可执行的识别方案

**日期：** 2026-08-05

**状态：** 设计性、非冻结、不可直接启动。本文件不修改任何已封存 campaign，
也不把未执行的方案当作经验结果。

**当前策略边界：** 现阶段唯一获准的新 GPU 工作，是在一块明确的非 sm_89
GPU 上运行第二架构的支持性探测和 304 单元可行性审计；不允许在那里计时。
下面涉及性能、迁移、抽象层和搜索收敛的实验，都需要当前论文之后的新 campaign
ID、预注册和明确授权。

## 核心结论

四个问题都能研究，但原始问法不能直接从一次 benchmark 推到一般结论。每个问题
都必须先改写成一个有限、可识别的估计目标：

| 原始问题 | 可由实验回答的版本 |
|---|---|
| 是否有 DSL 具有更高性能上限？ | 在冻结任务总体、硬件、正确性契约和完整有限候选空间内，哪个实现通道具有更低的、经独立确认的前沿延迟？ |
| 优化轨迹是否可迁移？ | 一个供体轨迹的每个机制和前缀，能否在目标通道中保持语义、通过门控，并保留逐步及累计收益？ |
| TileLang 低抽象层是否提高效率？ | 在算法、硬件指令路径和调度参数匹配时，较低抽象层是否改善运行时；它是否另行改变表达或搜索成本？ |
| 简单内核是否更快收敛？ | 在搜索者、信息、预算和终点相同的条件下，预先定义的优化决策复杂度是否增加达到冻结性能目标所需的尝试或时间？ |

最重要的设计原则是：**不要让一个实验同时回答可表达性、运行性能、搜索成本和
理论能力四个不同问题。**

## 1. 通用推理框架

一个 GPU DSL 主张至少需要以下推理链：

```text
定义问题总体和估计目标
  -> 候选实现执行相同的语义工作
  -> 实验处理只改变目标因素
  -> 所有请求结果都保留在完整分母中
  -> 正确性在与候选无关的冻结门控内成立
  -> 选择数据与确认数据分离
  -> 效应越过实验测得的分辨率下限
  -> 独立实验单元覆盖主张希望泛化的总体
  -> 才能得到有限范围内的结论
```

任何缺失环节都会缩小结论：

- 没有完整分母，只能描述幸存实现；
- 没有因素隔离，只能报告组合变化；
- 没有新确认，只能报告搜索结果；
- 没有多任务或多架构，只能报告局部单元；
- 没有等效性检验，`no significant difference` 不能证明“相同”；
- 没有执行，设计文件不能贡献经验结论。

### 所有后继实验共享的最低控制

1. 在实现和执行前冻结任务、形状、输入域、候选分母、硬件、工具链、门控、
   随机化、估计量、停止规则和排除规则。
2. 将 `UNSUPPORTED`、`BUILD_FAILED`、`LAUNCH_FAILED`、`GATE_FAILED` 和
   `GATE_PASSED` 保留为不同终止状态；失败消耗其预注册预算。
3. 正确性门控使用与候选实现无关的锚点、隔离的校准/调优/终端留出集，以及
   结构、语义和数值视角。
4. 搜索、选择和最终确认使用不同进程与不同数据；选择后不能人工替换。
5. 以进程、独立搜索轨迹或任务族为实验单元；试次和张量元素不是独立重复。
6. 每块硬件运行逐字节相同实现的重复标签空对照，并把所得分辨率下限
   `delta_hw` 写入发表规则。
7. 对确认性比较族预注册多重比较控制；探索性区间必须明确标注。
8. 记录并约束 GPU UUID、驱动、时钟、功耗和温度状态；若无法锁定时钟，则使用
   入场区间、随机区组和漂移诊断。
9. 用非控制性 pilot 估计方差和功效，在查看终端留出数据前冻结重复数；不凭空
   指定一个看似严谨的样本量。
10. 生成内容寻址的源码、运行锁、逐阶段收据、完整记录 census、分析结果和可独立
    验证的证据归档。

## 2. Q1：是否有 DSL 具有更高的性能上限？

### 2.1 从问题到结论的推理

**术语边界。** 当前四个实现通道并不等于四个 DSL：Triton 和 TileLang 是本问题
中的 DSL，CUDA-no-PTX 与 CUDA-unlimited 是实现层对照。四通道数据可以研究机制
和实现前沿，但“DSL 排名”必须明确只指预注册的 DSL 集合。

经验实验不能证明某种语言的理论上限。可检验结论应当是：

> 在预注册的任务总体和完整有限候选空间中，在相同硬件、正确性契约和确认协议
> 下，实现通道 `d` 的已实现性能前沿是否优于其他通道？

推理链为：

```text
相同任务与正确性契约
  -> 每个通道面对同一个抽象候选分母
  -> 完整审计可表达性和硬件可行性
  -> 在共同可达集合中进行独立选择和确认
  -> 在多个任务族、形状和架构上得到配对前沿
  -> 效应越过各硬件的空对照下限
  -> 才能主张该冻结总体中的前沿优势
```

### 2.2 当前推理链缺少什么？

| 环节 | 当前证据 | 缺失部分 |
|---|---|---|
| 完整分母 | `crossed_v2r3` 完成 304/304 单元审计。 | 只有一个融合算子和一个形状。 |
| 正确性 | 249 个单元通过冻结门控。 | 不能代表其他算子和输入域。 |
| 独立计时 | 498 条筛选、1,380 条确认和 60 条 sham 均完整。 | 只在 Ada 上执行；应用时钟未锁定。 |
| 稳定排名 | `g01` 上 TileLang 更快，`g05` 上 Triton 更快。 | 已观察到方向反转，不能推出通用胜者。 |
| 跨总体泛化 | 尚无。 | 缺多任务、形状、架构和独立任务族层面的推断。 |
| “上限”识别 | 有一个冻结的 4×4×19 候选空间。 | 它是有限设计空间前沿，不是理论语言上限或开放式调优上限。 |

### 2.3 实验 F0：第二架构可达性复现（当前唯一获准）

**目的。** 检验 Ada 上的可达性分母是否依赖架构；不回答性能排名。

**设置。** 在明确的非 sm_89 GPU 上创建硬件绑定后继，保持四策略、四通道、
19 网格和冻结门控不变，形成 `4 × 4 × 19 = 304` 个请求单元。

**实施。** 只运行源码保留的支持性探测，以及 build/setup/launch/gate 审计；
封存 GPU 身份、工具链、源码哈希、完整终止状态和 304 单元 census。

**对照理由。** 完全相同的请求分母使“架构”成为主要变化因素；保留失败阶段可以
区分公共 API 限制、架构资源限制和错误输出。

**允许的结论。** 可报告跨两种架构的可达性集合、交集和失败阶段变化。

**不允许的结论。** 不得从该实验推断哪种通道在第二架构上更快。

### 2.4 实验 F1：多任务有限前沿实验（论文后、新授权）

**目标总体。** 从公开、预先冻结的算子采样框中按计算模式分层选择任务；至少覆盖
归约、归一化、卷积、矩阵乘、融合矩阵乘和注意力。每个算子族预注册三个规模和
两个输入域。算子族是顶层泛化单元，形状和输入域嵌套于算子族，不能伪装成独立
任务重复。

**处理与固定因素。** 对每个任务定义一个 DSL 无关的有限候选语法，包括算法、
算术、tile、pipeline、布局、融合位置和启动几何。四个实现通道面对同一份语义
候选 manifest；工具链和源码按架构冻结。禁止执行中追加“看起来有希望”的候选。

**两个分开的估计目标。**

1. **共同可达前沿：** 只在四通道均可表达、构建、启动并通过门控的候选交集中
   比较时间；用于隔离实现差异。
2. **可达性覆盖：** 分别报告每个通道在完整请求分母中的终止状态；不得把
   `UNSUPPORTED` 人为换算成一个很慢的时间并混入性能均值。

**执行阶段。**

1. **Audit：** 完整枚举 `任务 × 形状 × 输入域 × 架构 × 通道 × 候选`。
2. **Screen：** 每个 gate-legal 候选使用两个全新进程；每个通道机械选择前三名。
3. **Selection-confirm：** 在新的随机区组中只比较前三名，锁定一个赢家。
4. **Terminal-confirm：** 再用全新进程估计已锁定赢家；最终数据不再参与选择。
5. **Sham：** 每块架构让逐字节相同实现的两个标签通过全部计时路径。

第三阶段的存在很重要：如果直接在最终确认数据中再选最小值，所谓“前沿”仍会
受到 winner's curse 影响。

**主要量。** 对任务单元 `u` 和通道 `d,e`，定义已锁定赢家的配对对数比：

```text
theta[u,d,e] = log(T[u,d] / T[u,e])
```

`theta < 0` 表示 `d` 更快。局部优势只有在整个确认区间低于
`-delta_hw` 时成立。跨任务结论使用算子族聚类的配对分析；形状、输入域和重复
进程留在族内。架构交互先于合并结果报告。

跨架构汇总时先定义分辨率调整后的量
`z[u,d,e] = theta[u,d,e] + delta_hw[architecture(u)]`；`z < 0` 才表示优势已经
越过该架构自己的测量下限，不能把 Ada 的 sham 数字直接套到另一块硬件。

**判定规则。**

- **局部前沿优势：** 单个任务单元的完整区间越过 `delta_hw`。
- **冻结总体的平均优势：** `z` 的算子族聚类区间对每个预注册竞争通道均完全
  低于 0，并通过多重比较控制。
- **一致支配：** 每个预注册任务—架构单元都同向越过下限；只要存在可靠方向
  反转，就不得使用“普遍更高上限”。
- 未满足上述规则时，应报告异质前沿和交互，而不是选一个平均赢家。

**这个实验最终能回答什么？** 它能回答“在这个公开任务总体和有限候选语法中，
哪个通道实现了更高前沿”，仍不能回答语言的理论上限。

## 3. Q2：优化轨迹是否可以迁移？

### 3.1 从问题到结论的推理

“最终配方可以重写”与“优化轨迹可以迁移”是不同主张。轨迹包含步骤顺序、每步
机制、前置条件、失败路径和重调优成本。完整推理链为：

```text
供体轨迹在当前门控内有效
  -> 每一步只引入一个可命名机制
  -> 每个前缀被语义等价地翻译到目标通道
  -> 目标前缀通过独立正确性门控
  -> 与目标自身的前一前缀配对计时
  -> 逐步和累计收益在全新确认中保留
  -> donor order 优于有效的顺序对照
  -> 才能说“有序轨迹”而非“最终想法”可迁移
```

### 3.2 当前推理链缺少什么？

| 环节 | 当前证据 | 缺失部分 |
|---|---|---|
| 策略可表达 | 三种融合策略在四通道的 15 个网格上共同可达。 | 没有逐步轨迹或收益保留。 |
| 历史供体正确性 | Phase-1 A/B/C/D 曾被用于迁移叙事。 | matmul-v4 中每条路径在两类各 512 个输入上全部失败，不能作为当前供体。 |
| 互惠设计 | `reciprocal_v2` 设计了 3 来源 × 4 目标 × 2 模式。 | 只有最终配方单元；没有可执行 ABI、源文件或结果。 |
| 轨迹顺序 | 无控制性证据。 | 没有翻译每个前缀，也没有顺序对照。 |
| 翻译者效应 | 纠正设计默认一个翻译者。 | 结论只能以该翻译者为条件；不能泛化为翻译者无关。 |

现有 24 单元纠正设计最多能研究**最终配方迁移**。即使它被完整执行，也不能仅凭
24 个最终实现回答“有序轨迹是否迁移”。

### 3.3 实验 T0：建立合法供体轨迹

**设置。** 在当前、与候选无关的门控内，前瞻性地产生至少三个来源通道的供体
轨迹。每条轨迹从同一语义基线开始，记为 `p[o,0] ... p[o,L_o]`。

**步骤契约。** 每个 `p[o,k-1] -> p[o,k]` 必须只引入一个具名机制，并冻结：

- 机制、前置条件和不允许改变的语义；
- 允许目标通道采用的最小合法 lowering；
- 预期动态工作、内存流量和关键硬件指令；
- 源码、构建产物、门控结果和供体上的独立性能效应。

若一步同时改变精度、tile 和 pipeline，就必须拆成三个步骤，或者将其标记为不可
识别的组合处理。只有供体自身的确认区间越过 `delta_hw` 的步骤，才进入“收益
是否迁移”的主要分析；其余步骤仍保留用于表达性分析。

**设计理由。** 先建立当前门控合法的供体，避免把共享错误或事后挑选的成功配方
带入迁移实验。

### 3.4 实验 T1：前缀级互惠迁移

**实验单元。**

```text
(operator, origin o, prefix k, destination d,
 transfer mode m, translator r, order arm q)
```

对单个算子，基础单元数为
`[sum_o(L_o + 1)] × 4 destinations × 2 modes × R translators`，再加冻结的
顺序对照子集；不能继续沿用只含最终配方的固定 24 单元数字。

**因素。**

- `destination`：TileLang、Triton、CUDA-no-PTX、CUDA-unlimited；自迁移作为
  管线正对照保留。
- `mode=literal`：只允许语法和目标 API 所必需的 lowering，不做性能搜索；这是
  主要因果臂。
- `mode=retuned`：每个来源绑定同样大小的候选 manifest，失败消耗尝试；如果
  retune grid 不能识别来源效应，则只作描述性结果。
- `translator`：一个翻译者只能支持“以该翻译者为条件”的结论；若要估计翻译者
  变异，需要至少两个真正隔离、收据绑定的实现者，并重新冻结 census。
- `order`：对具有至少三个可交换步骤的轨迹，增加一个保持依赖关系的随机拓扑
  顺序；不要使用违反前置条件的简单倒序。

**执行。** 每个前缀依次经过源码/配置/动态工作/生成代码审计和终端正确性门控；
literal 单元一次尝试，retuned 单元完整执行冻结候选数。所有合格实现先筛选，再
锁定选择，并在 15 个或经功效分析确定的全新随机区组中确认。

**主要量。** 目标通道中第 `k` 步的配对收益为：

```text
g[o,d,k] = log(T[o,d,k-1] / T[o,d,k])
```

`g > 0` 表示该步骤加速。累计收益为：

```text
G[o,d] = log(T[o,d,0] / T[o,d,L_o])
```

同时报告：每个前缀的终止状态、逐步收益、累计收益、与供体收益之差，以及 donor
order 相对拓扑顺序对照的到达曲线。不要用一个相关系数替代这些不同终点。

**判定和分类。**

- **idea-portable：** 机制在目标通道中可表达且通过门控；
- **schedule-portable：** literal 步骤的完整收益区间高于 `delta_hw`；
- **destination-adaptive：** literal 不成立，但在同预算 retune 后成立；
- **resource-limited：** 源码可表达，但冻结候选在 build/setup/launch 阶段受资源
  约束；不得重标为 `UNSUPPORTED`；
- **incorrect-translation：** 可以构建和启动，但不能通过冻结正确性门控；
- **lane-locked：** 只有保留源码的支持探测在全部许可路径上确认源码层面
  `UNSUPPORTED` 时才使用；
- **ordered-trajectory portable：** 多个前缀的收益和累计收益均成立，且 donor order
  明确优于有效顺序对照。

标准矩阵乘上的一次实验只能建立该算子内的分类。若要给出跨 GPU DSL 的一般迁移
结论，还必须在多个独立算子族上复制，并以算子族为聚类单元。

## 4. Q3：TileLang 的较低抽象层级是否提高效率？

### 4.1 先拆开三个不同结论

“效率”至少有三种含义，必须分别研究：

1. **运行效率：** 相同算法和硬件路径下，低层表示是否生成更快代码；
2. **表达/搜索效率：** 达到目标实现需要多少代码、编译、调试和候选尝试；
3. **能力效应：** 低层 API 是否开放了高层无法表达的数据流或硬件操作。

第三种情况下工作图已经改变，不能把速度差解释为“抽象开销”。

### 4.2 运行效率的推理链与缺口

```text
相同算子、输入和数值契约
  -> 相同算法、tile、pipeline depth、线程数和硬件指令族
  -> 唯一预期差异是 TileLang 表达层级
  -> 动态工作和生成代码审计确认比较仍然匹配
  -> 随机区组内配对计时并越过 sham 下限
  -> 在多个任务和实现者上重复
  -> 才能得到抽象层运行效率结论
```

当前历史 matmul 比较在 depth=2 上得到 `H1=0.995 ms`、`M2=1.071 ms`；低层方向
上慢 7.7%，但落入预注册的 3%–10% 空档，正式结果是 `no verdict`。它还缺少：

- matmul-v4 下的重新裁定；
- 多算子、多形状和多实现者复制；
- 对“没有改善”的等效性检验；
- 纯高层调度开销对比，因为历史 `H2` 仍发出 `cp.async`，而 `M1` 不发出；
- 独立的搜索成本测量。

### 4.3 实验 A1：匹配的 TileLang 抽象层运行时实验

**任务。** 预注册至少三个具有高层和中层等价实现的算子族，并为每族选择三个
形状。标准 matmul 必须使用当前 matmul-v4 门控。不能构造匹配对的任务进入
“能力效应”附录，不进入抽象开销估计。

**处理。** 在每个任务内构造 `TL-H` 与 `TL-M` 配对。固定算法、数值类型、tile、
pipeline depth、线程数、张量核指令族和逻辑内存流量。抽象层是唯一预期处理。

**实现者控制。** 至少两个相互隔离的实现者分别完成两层实现，层级实现顺序在
实现者内随机化。若只用一个实现者，结论必须明确以该实现者为条件。

**配对入场审计。** 每对实现必须：

- 通过同一终端正确性门控；
- 执行相同的动态数学工作和相同硬件指令族；
- 绑定源码、IR/PTX/SASS、共享内存、寄存器和全局流量；
- 对任何算法、pipeline 或硬件路径漂移失败关闭。

生成代码不必逐字节相同，因为代码生成差异正是处理可能生效的路径；但计算工作
必须可比。

**计时。** 固定候选无需搜索。每对在全新进程的随机完整区组中计时，顺序在区组
内随机化；重复数由独立 pilot 的进程级方差和预注册最小相关效应决定。重复标签
sham 同路执行。

**主要量。** 对匹配单元 `u`：

```text
a[u] = log(T_low[u] / T_high[u])
```

- `a` 的完整区间低于 `-delta_hw`：低层运行时更快；
- 完整区间高于 `delta_hw`：高层运行时更快；
- 完整区间位于预注册等效区间 `[-epsilon, +epsilon]`：支持运行等效；
- 其他结果均为不确定，不能把“不显著”写成“没有抽象开销”。

`epsilon` 必须不小于实测 sham 分辨率，并在终端数据前冻结。跨任务结论以算子族
聚类，并报告层级与形状/算子的交互。

### 4.4 实验 A2：抽象层搜索成本实验

**目的。** 回答“高层还是低层更容易找到高效实现”，而不是代码本身谁更快。

**设计。** 将独立实现者或冻结模型版本随机分配到 `TL-H only` 与 `TL-M only`
起始环境。两臂接收相同任务说明、正确性反馈、候选数、墙钟上限和硬件。终端目标
是 A1 中预先冻结的 gate-legal 参考，不向搜索者泄露终端数据。

**结果。** 主要报告首次到达参考性能 5% 内所需的候选尝试；编译时间、主动 GPU
时间、token、源码修改量和失败数为并列资源指标。低层如果只在允许新算法后更快，
应归入能力效应，而不是抽象开销。

## 5. Q4：简单内核是否比复杂内核更快收敛？

### 5.1 原问题中隐藏的识别问题

“简单”不是现成处理，“收敛”也不是观测到最后一个候选。历史表格中的 sum、
matmul 和 SDPA 同时改变了：

- 算子语义和可用优化机制；
- 提示与先验信息；
- 编译和参考实现成本；
- 失败率、搜索预算和最终最好点质量。

因此，历史上 `1.0 -> 4.75` 次迭代的趋势是生成假设的描述性证据，不是复杂度的
因果效应。已退役的 `convergence_v2` 没有启动，也不能复活使用。

### 5.2 可辩护的结论

应把问题改写为：

> 在搜索者、信息、候选预算、门控和终端目标相同的情况下，较多且相互依赖的
> 优化决策是否增加首次找到合格近前沿实现所需的尝试或主动时间？

这会把“复杂内核”变成可测量的**优化决策复杂度**。它不能单独证明复杂算子的
语义本身导致慢收敛，但能识别社区真正关心的搜索负担。

### 5.3 推理链和缺失环节

```text
复杂度在看到搜索结果之前定义
  -> 搜索者、提示、工具、预算和反馈固定
  -> 每个任务有独立冻结的 gate-legal 参考
  -> 多个独立随机轨迹运行到成功或删失
  -> 终端留出在轨迹结束后离线判定首次成功点
  -> 失败和预算耗尽被保留
  -> 复杂度与 time-to-event 的关联或因果效应被估计
```

当前缺少实际独立轨迹、外生复杂度定义、统一参考、平衡预算和执行数据。历史轨迹
中的“最终最好点”由同一条有限搜索产生，也可能把提前停止误认为收敛。

### 5.4 实验 C1：预注册的跨任务关联实验

**作用。** 检验真实公开任务中，决策复杂度与搜索速度是否相关；它本身仍不是
完全随机化的复杂度因果实验。

**任务抽样。** 从公开采样框按计算模式分层选取算子。独立评审者在看不到任何
新搜索结果的情况下，为每个任务冻结：

- 可独立选择的优化轴数；
- 轴之间的前置依赖深度；
- 正确性约束数；
- 资源约束和可达候选比例。

预先组合成复杂度分层；不得依据后续所需迭代数重新标注“简单/复杂”。

**搜索控制。** 使用同一不可变搜索模型/实现者协议、neutral prompt、工具接口、
可见反馈、最大候选数和主动时间预算。每个任务—通道单元运行多个独立轨迹；
GPU UUID 在重复间平衡，轨迹彼此不能查看源码或性能结果。

**终点。** 主要终点是：首次产生“终端门控合法且位于冻结参考延迟 5% 内”的
候选所需的尝试数。终端留出只在轨迹结束后离线评估所有保留候选，搜索者只看到
独立调优门控。主动 build/evaluate 秒数、token 和失败数作为次要终点。

**分析。** 把预算耗尽视为右删失，不把失败轨迹删除。按复杂度层报告
Kaplan–Meier 曲线和冻结 `tau` 下的 restricted mean attempts/time；任务族作为
聚类或分层单元，多重比较使用 Holm 校正。

### 5.5 实验 C2：任务内随机化的决策空间复杂度实验

**作用。** 补上 C1 无法提供的因果环节。

**处理。** 在同一个任务、通道和终端参考内，构造包含相同已知近前沿候选的搜索
空间，但随机开放不同数量的优化决策轴，例如：

- `C1`：其余参数固定，只开放一个轴；
- `C3`：开放三个轴；
- `C6`：开放六个轴及其冻结依赖关系。

三臂拥有同一个可达到的目标；差异只是搜索者必须解决的选择数量。每个独立搜索
轨迹随机分配复杂度臂，使用相同提示模板、模型版本、反馈和预算。

**负对照。** 将完全相同的搜索空间赋予两个不同的“simple/complex”标签，但不把
标签暴露为机制提示；若出现系统差异，说明编排或分析存在标签效应。

**敏感性正对照。** 对少量预注册任务提供一个有效机制提示；它应降低到达时间，
用于证明实验能够检测已知的信息优势，但不进入复杂度主效应。

**判定。** 只有在任务内随机比较显示随着开放决策轴增加，restricted mean
attempts/time 单调增加，并且确认区间和多重比较规则均通过时，才能说“决策空间
复杂度因果性地减慢有限预算搜索”。

若只有 C1 成立，应写成相关性；若只有 C2 成立，应限于构造的搜索空间。两者方向
一致，才构成对社区更可泛化的机制证据。

### 5.6 新 campaign 的必要条件

该工作必须使用新 ID，不能复制或解除 `convergence_v2` 的退休状态。启动前至少要
具备：冻结的复杂度定义、当前鲁棒门控、独立调优/终端数据、gate-legal 参考、不可
变搜索模型或实现者协议、GPU 身份、控制性 `tau`、功效决定的重复数和远程预注册
收据。

## 结论

完成推理链的关键不是增加更多计时，而是让每个实验只承担一个清楚的识别任务：

- F1 识别有限候选空间中的前沿，而不是理论上限；
- T1 识别每一步和顺序的迁移，而不是只重写最终配方；
- A1/A2 分开识别代码运行效率和搜索效率；
- C1/C2 分开识别真实任务相关性和可随机化的决策复杂度因果效应。

这样得到的结果即使是否定或异质的，也会给社区留下可复用知识：哪些机制能表达、
哪些收益能迁移、抽象层影响的是代码还是搜索，以及复杂度究竟在哪个环节消耗优化
预算。
