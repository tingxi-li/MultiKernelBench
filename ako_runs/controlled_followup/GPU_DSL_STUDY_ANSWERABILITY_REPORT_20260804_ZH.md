# GPU DSL 研究究竟能回答什么问题？

## 可回答的问题、受控实验与当前主张边界

**日期：** 2026-08-04

**状态：** 中期、非冻结技术报告。本报告不是受策略门控的论文。

**控制性融合算子结果：** `crossed_v2r3`

**审阅的仓库状态：** 分支 `cross-dsl-6op-ncu-redo` 上的提交
`4e8c49a7696a933da50f0e1e06d8e31f48643bcb`。

## 核心回答

可以，GPU DSL 研究能够回答重要问题，但具有科学价值的问题比“哪个 DSL
最好？”更为具体。在指定的 Ada 硬件和冻结的软件栈上，现有证据可以回答：

1. 请求的优化策略能否通过固定的公共实现路径在源码层面表达；
2. 哪些请求的启动配置能够构建、启动并通过冻结的正确性契约；
3. 可行性失败发生在哪一阶段，以及其原因是 API 限制、硬件资源上限、启动
   失败还是输出错误；
4. 某个被单独隔离的实现机制是否会改变特定实现通道和网格配置上的性能；
5. 特定单元的通道对比是否大于测量流水线已经证实的分辨率；以及
6. 历史产物是否仍满足更新后的、与候选实现无关的正确性契约。

这些回答对社区有价值，因为它们以可复现的能力、可行性、正确性和实现性能
说明，取代了单一的胜者排名表。控制性实验审计了全部 304 个请求的融合算子
单元，保留了 249 个 `GATE_PASSED`、36 个 `BUILD_FAILED` 和 19 个
`UNSUPPORTED` 结果。随后，实验生成了 498 条筛选记录和 1,380 条确认记录，
其中包括 60 条重复标签空对照（sham）记录。包含 2,638 个条目的证据归档可被
独立验证。

同一项研究目前不能回答哪个 DSL 通常最快、Ada 上的可达性前沿是否会在另一种
架构上保持不变、优化配方能否跨 DSL 迁移、工程投入如何改变前沿，也不能回答
计时结果能否跨输入分布泛化。这些问题缺少相应实验，而不只是需要附加几句
不便的限定语。

## 1. GPU DSL 主张的最小可回答单元

一个可辩护的 GPU DSL 结果不能只用语言名称来索引。它的最小可回答单元是：

```text
(算子, 策略, 实现通道, 网格配置, 硬件, 工具链,
 正确性契约, 输入分布, 估计量)
```

只有当某个分量在实验中被改变，或者其泛化另有充分依据时，研究才能对该分量
进行泛化。固定硬件不能证明架构可移植性；只计时一个输入分布不能证明分布
稳定性；比较两个同时改变放置位置和后处理方式的实现，也无法隔离其中任一
机制。

由此可以得到一条实用的证据阶梯：

```text
请求的实验单元
  -> 能否在源码层面表达？
  -> 能否在指定硬件上构建并启动？
  -> 能否通过冻结的正确性契约？
  -> 是否在没有人工替换的情况下被选中？
  -> 是否在全新进程中得到确认？
  -> 整个区间是否越过空对照分辨率下限？
```

跳过其中任何一级都会改变所回答的问题。源码限制不是慢内核；受资源约束的
构建失败不是语言限制；通过门控的单元并不等于对所有输入都正确；置信区间
排除 1，也不一定意味着完整基准流水线能够分辨该效应。

## 2. 本研究目前能够回答的问题

| 研究问题 | 当前有证据支持的回答 | 允许的主张范围 |
|---|---|---|
| 此前有争议的通道/策略路径能否表达？ | 保留源码的探测实验确认：固定的 CUDA-no-PTX 寄存器路径在全部 19 个网格配置上成立；Triton 显式共享内存路径在全部 19 个网格配置上表现出同一个公共 API 限制。 | 仅限这些实现、API、版本和策略；不是关于 CUDA、Triton 或 TileLang 的语言定理。 |
| 有限的 Ada 可达性前沿是什么？ | 完整审计保留了 304/304 个结果。`register_fused`、`global_intermediate` 和 `register_common_postprocess` 在 15 个网格配置上可由四个通道共同达到；`smem_staged` 没有四通道共同可达的网格。 | 限于 RTX 6000 Ada、冻结的 19 网格预算、源码包和工具链。 |

| 可启动的单元是否满足指定算子契约？ | 249 个有资格进入计时的单元全部通过四种用例、64 个留出种子和两个门控视角，共产生 127,488 条绑定的门控记录。 | 只能说明符合这一有限、冻结的门控，不能说明对所有输入都正确。 |
| 固定行 softmax 后，bias/GELU 的放置是否影响时间？ | 在局部条件下是。Triton 中，register-common/global 在 `g01` 上为 1.064220，在 `g05` 上为 0.978482；两个精确区间都越过空对照下限，并且方向相反。 | 仅限两个特定单元、正值分布下的放置对比；不是通用的放置方式排名。 |

| 证据和分析能否被独立检查？ | 可以。归档中的 2,638 个条目全部验证通过，独立重新推导的最终摘要与封存摘要逐字节相同。 | 说明保留证据和分析器的可复现性，不代表外部有效性。 |

## 3. 学术价值与可泛化知识

### 3.1 可表达性是分母，不是脚注

性能表通常只考虑已经成功编写、构建并启动的代码。这会隐藏系统无法表达或
无法在硬件预算内实现的策略，使幸存的实现看起来像整个设计空间。

可泛化的贡献是同时公布请求的分母和进入计时的分子。这样，“不支持”不再是
非正式的托辞，而成为可测量的结果；公平性能比较所依赖的共同交集也会显式
呈现出来。

### 3.2 可达性是集合值，而不是标量

一个 DSL 并不存在单一的标量能力分数。其可观测能力是一组可达的
`(策略, 网格配置, 硬件, 工具链)` 单元；跨 DSL 比较依赖这些集合的交集。
某个策略可能在源码层面可以表达，却因为资源限制而无法在特定网格上实现，
因此“支持”与“成功”必须保留为两个不同维度。

这种集合值视角也适用于稀疏系统、量化 DSL、分布式运行时、向量化工具和
编译器功能研究。它能防止一个最优幸存点冒充整个编程系统。

### 3.3 机制间交互本身就是结果

Triton 的放置对比在 `g01` 和 `g05` 之间发生方向反转。因此，答案不是
“寄存器放置胜出”，也不是“全局放置胜出”，而是：在这一实现族中，放置
方式与启动网格存在交互。

这是对社区有用的知识：当效应方向在合法配置之间反转时，把它们平均成一个
全局排名会丢弃实验实际揭示的机制。

### 3.4 正确性必须置于优化过程之内

历史矩阵乘研究在其旧门控下显示，性能跨度从 7.0× 收缩至 1.31×。随后，
matmul-v4 证明四个 A/B/C/D 产物在两个注册用例上具有共同失败。历史数字仍可
作为归一化方法的诊断，但它不是当前经过正确性认证的前沿。

比旧计时数字更持久的结论是：算术、调度和搜索的归一化必须在当前正确性契约
内部完成。即使多个实现产生逐字节相同的结果，只要它们共享同一个未被触发的
错误，也不能据此确立正确性。

### 3.5 测量分辨率应由实验给出

统计区间描述分析模型下的抽样不确定性，却不能说明在真实零效应下，完整的
构建、进程、顺序和计时流水线会产生多大变异。给同一个逐字节相同的实现赋予
两个重复标签，可以提供这一零效应对照。

要求真实对比的整个区间越过空对照下限，便可把分辨率变成预注册的发表规则。
这一思想适用于任何可能因进程状态、时钟、编译、顺序或测试框架逻辑而产生
微小表观效应的系统基准。

### 3.6 实验失败也是证据的一部分

三个冻结的前序实验分别在保留单元结果之前、完整审计之后以及完整筛选之后
失败。用事件收据保存每次失败，可使分析器和编排缺陷保持可见；在新锁下修复，
则可防止有利的部分结果被悄然提升为控制性结果。

这为经验系统研究提供了一条通用恢复规则：将分析器与实验一起冻结，保存失败
闭包，说明其科学后果，并重新运行该缺陷可能影响的所有下游阶段。

## 4. 为什么这些回答来自受控实验

| 有效性威胁 | 采用的控制 | 设计理由 |
|---|---|---|
| 幸存者偏差 | 在计时前审计完整的 `4 × 4 × 19` 笛卡尔积。 | 失败和不支持的请求仍保留在分母中。 |
| 仅靠声明判定“不支持” | 运行 19 网格、保留源码的支持性探测。 | 重复保存的证据可以区分固定 API 限制和遗漏的工程实现。 |
| 把资源失败误标为语言失败 | 分别保留各类终止状态。 | 失败发生的阶段决定了可以辩护的因果解释。 |
| 实验处理混杂 | 增加 register-common 桥接策略，固定行 softmax 源码和启动几何。 | 当两个机制同时变化时，增加重复次数也无法判断究竟哪个机制产生了效应。 |
| 正确性标准随候选实现而调整 | 使用具名、与候选实现无关的锚点校准，并锁定按域分离的验证种子。 | 候选实现的误差不能反过来设定其自身的验收阈值。 |
| 重用搜索结果并进行人工选择 | 使用双进程筛选、机械化的“前二名加 `g01`”选择以及全新确认过程。 | 搜索测量负责选择候选，另外的全新进程负责估计所选对比。 |
| 伪重复 | 使用进程级配对比和种子级配对。 | 试次、张量元素、候选实现和重复的门控视角都不是独立实验单元。 |
| 计时瞬态和顺序效应 | 预先冻结随机区组和试次 60–99，并保留全窗口及漂移诊断。 | 仅完成预热不能证明早期计时试次已经稳定。 |
| 效应低于仪器分辨率 | 运行逐字节相同实现的重复标签空对照。 | 当流水线在零效应下表现出同等大小的变异时，不发表微小的非零区间。 |
| 事后修复分析 | 在执行前绑定源码、分析器、锁、硬件身份、记录数和事件策略。 | 分析变更可能改变资格判定、候选选择和最终报告的效应。 |

这些控制降低了特定威胁，但并未消除全部不确定性。应用时钟没有锁定，也没有
执行温度准入区间；28 个区间是逐对比区间，而不是控制族错误率的联合区间；
可报告的计时效应只使用一个正值 `rand`、种子 0 输入。

## 5. 完整实验示例

### 示例 A——DSL 能否表达请求的策略？

**设置。** 冻结一个融合算子：在 `M=1024`、`N=8192`、`K=8192` 下执行
GEMM+bias+精确 erf-GELU+行 softmax，并使用四种策略、四个实现通道和 19 个
启动网格。

**设计。** 用 19 网格、保留源码的探测实验解决两个有争议的源码层面主张，
然后审计完整的 304 单元笛卡尔积。每个单元只能获得一个终止结果。

**实施。** CUDA-no-PTX 寄存器放置通过全部 19 个探测。Triton 显式用户管理
共享内存在全部 19 个探测中产生同一个已捕获的公共 API 限制。完整的
[`审计摘要`](fused_epilogue_crossed_v2/results/crossed_v2r3/audit_summary.json)
保留了 304 个结果，并为 249 个通过单元保留了 127,488 条门控记录。

**理由。** 完整笛卡尔积可防止快速幸存实现代表整个 DSL。独立探测用于区分
源码可表达性与工程遗漏，终止状态则用于区分 API 边界、资源上限和错误结果。

**回答。** 三种策略在全部四个通道上共享 15 个可达网格；`smem_staged`
不存在四通道共同可达的网格。

**边界。** 这是有限的 Ada/工具链/源码前沿，不是理论上的语言上限。

### 示例 B——后处理放置是否影响性能？

**设置。** 比较 `global_intermediate` 和 `register_common_postprocess`。前者在
公共后处理中执行 bias/GELU，后者把 bias/GELU 移入通道原生的累加器代码。
两者绑定相同、带检查的行 softmax 源码和启动几何。

**设计。** 在同一通道和同一网格内构造配对对比，使放置成为预期的唯一变化
因素。仅允许通过门控的单元进入，机械化选择确认单元，并要求整个区间越过
空对照下限。

**实施。** 每个门控合法单元都在两个全新进程中筛选。确认阶段采用 15 个随机
区组和进程级预定尾段中位数。控制性估计见
[`最终摘要`](fused_epilogue_crossed_v2/results/crossed_v2r3/final_summary.json)。

**理由。** 前序实验同时改变了放置方式和 softmax 所属实现。增加重复次数只会
更精确地估计这个混杂的整体。桥接策略通过固定行 softmax 改变了估计目标。

**回答。** Triton 中，register-common/global 在 `g01` 上为 1.064220，区间
为 `[1.017226, 1.096966]`；在 `g05` 上为 0.978482，区间为
`[0.970593, 0.982281]`。放置方式与网格存在交互。

**边界。** 只有这两个正值分布下的放置对比满足报告规则；不能推出通用的
放置方式排序。

### 示例 C——历史优化产物是否仍然正确？

**设置。** 取冻结的四条 Phase-1 A/B/C/D 矩阵乘路径，用 matmul-v4 的六个
用例、与候选实现无关的具名锚点以及语义和契约符合性视角对其进行评估。

**设计。** v3 在 64 个 `opposing_means` 验证种子中失败 2 个后，使用新命名空间，
为每个用例设置 640 个校准种子和 512 个验证种子。校准完成且门控规范被冻结
之前，验证数据保持隔离。对每个门控中的 24 个用例/指标族，校准规模满足
`24 × 0.99^640 = 0.0386132 < 0.05`；512 个验证种子零失败时，预注册的
Bonferroni 校正后逐用例上界为 `0.009307`。

**实施。** 仪器审计完成全部 66,852 条预期唯一记录，没有缺失、重复、意外或
绑定失败。[`matmul-v4 摘要`](robust_gate/audits/matmul_v4_instrument_v1/results/summary.json)
记录了每条 A/B/C/D 路径在全部 512 个 `legacy_u01` 和全部 512 个
`opposing_means` 输入上失败，同时通过全部四个有符号用例。

**理由。** 新命名空间防止重用失败留出集的信息；与候选实现无关的锚点防止
候选自我评分；逐用例报告避免把异质输入合并成一个看似令人放心的成功率。

**回答。** 历史 1.31× 前沿不符合 matmul-v4，若不重新执行门控内搜索，就不能
把它作为当前性能结论。

**边界。** 该结果否定的是这一门控下的这些产物，而不是所有 fp16 累加设计。

### 示例 D——哪些计时对比真正可被分辨？

**设置。** 对 249 个门控合法单元各使用两个全新进程进行筛选。每个策略/通道
选择前两个合法单元并加入合法的 `g01`，去重后得到 44 个单元；随后在 15 个
随机区组中确认正值和留出的有符号输入。每个进程在两秒预热和 L2 刷新后记录
100 个试次。

**设计。** 将筛选与确认分开，把试次 60–99 冻结为主窗口，在区组内进行配对
比较，并让同一个逐字节相同实现的两个标签通过完全相同的流水线。

**实施。** 筛选完成 498/498 条记录。确认阶段完成
`44 × 2 × 15 = 1,320` 条单元记录及 60 条空对照记录，共 1,380/1,380 条。
推断使用 15 个进程级配对比，而不是把 1,500 个试次视为独立样本。

**理由。** 分离的确认阶段减少直接重用搜索噪声；机械选择消除人工替换；随机化降低
固定顺序混杂，配对控制区组层面的变化。尾段窗口是针对前序计时轨迹的前瞻性
响应，并不证明平稳性。空对照检验完整流水线能否分辨所主张的效应。

**回答。** 空对照给出 0.014958 的绝对对数比下限。28 个预注册正值分布对比中，
18 个满足报告规则：两个放置对比和 16 个通道对比。

**边界。** 这些是单个正值计时输入上的逐对比区间。留出的有符号结果只用于
诊断；时钟没有锁定；空对照也无法揭示两个标签共同承受的偏差。

### 示例 E——冻结实验能否从分析器缺陷中恢复？

**设置。** 在 GPU 执行前绑定实验源码、分析器、依赖、硬件身份、预期记录数和
恢复规则。

**设计。** 如果冻结代码失败，保存其精确闭包，将其标记为非控制性结果，在新
源码包和新锁下修复，并重新运行该缺陷可能影响的每个下游阶段。

**实施。** `crossed_v2` 在保留单元结果前停止；`crossed_v2r1` 保留了完整审计，
但错误拒绝了有效的资源失败；`crossed_v2r2` 完成审计和筛选，却在确认选择前
失败。没有通过覆盖层提升任何部分选择或计时结果；`crossed_v2r3` 全新运行了
所有阶段。

**理由。** 分析器缺陷可能改变可行性统计、候选选择或最终主张。即使某些测量
仍逐字节相同，在查看结果树后进行修复也会引入研究者自由度。

**回答。** 后继实验完整结束，证据归档通过独立验证，重新推导的最终摘要也与
原摘要逐字节相同。[`结果备忘录`](fused_epilogue_crossed_v2/RESULT_CROSSED_V2R3_20260802.md)
绑定了完整事件链。

**边界。** 这证明了保留实验的可审计性，而不是跨硬件可复现性。

## 6. 本研究目前不能回答的问题

| 问题 | 尚未得到回答的原因 | 所需实验 |
|---|---|---|
| 可达性前沿能否跨架构泛化？ | 目前只有 sm_89 Ada 证据。 | 在冻结的非 sm_89 后继实验上运行策略授权的支持性探测和 304 单元可行性审计。 |
| 哪个 DSL 通常最快？ | 单个融合形状、单一架构、经过选择的单元以及特定单元上的交互，无法识别通用排序。 | 预注册的多算子、多形状、多架构研究，并显式声明估计目标和共同可达子集。 |
| 任何已观测到的“不支持”状态是否都是理论语言上限？ | 探测只覆盖固定的公共实现路径和版本。 | 扩大 API/版本覆盖，或者给出正式的语言能力论证。 |
| 作者投入和搜索成本会在多大程度上改变前沿？ | 编译观测只是描述性结果，投入前沿实验也没有控制性结果。 | 使用随机化或平衡的投入预算、重复搜索和预先声明的投入估计目标。 |
| 优化配方能否跨 DSL 迁移？ | 互惠迁移实验没有控制性执行结果。 | 平衡供体/受体翻译，冻结语义等价性，使用相等的重调优预算并进行全新确认。 |
| 不同 DSL 的搜索轨迹是否收敛？ | 收敛实验尚未启动即已退役。 | 需要一个以可达性前沿为条件、重新论证的新设计；退役协议不能贡献证据。 |
| 计时结论能否跨输入分布泛化？ | 可报告效应使用正值 `rand`、种子 0；留出的有符号计时只用于诊断。 | 按策略要求，另行资助并执行公共语料上的配对 `rand`/`randn` 研究。 |
| 通过门控的实现是否对所有输入都正确？ | 门控只覆盖有限用例和种子。 | 形式化验证，或覆盖范围更广且独立进行功效设计的验证域。 |

管辖后续工作的
[`策略文件`](LATER_WORK_POLICY_20260731.md)只授权第二架构的可行性实验，不授权
计时。它也把 RQ(e)、收敛、互惠迁移和投入前沿主张排除在当前论文范围之外。

## 7. 面向未来 GPU DSL 研究的可复用协议

1. 在开始实现前定义完整的请求分母。
2. 把源码可表达性、构建/设置、启动、正确性和计时划分为不同终止阶段。
3. 对有争议的能力主张使用保留源码的探测实验。
4. 使用与候选实现无关的锚点校准正确性，冻结不相交的验证输入，并对畸形证据
   采取失败关闭策略。
5. 增加桥接处理，直到每个性能对比只改变一个预期机制。
6. 在选择计时候选之前，审计完整的请求笛卡尔积。
7. 将搜索与确认分开，并机械化推导选择结果。
8. 识别真正的独立实验单元；它通常是进程或种子，而不是试次或张量元素。
9. 检查计时轨迹，预注册主窗口，随机化顺序，并在区组内配对比较。
10. 让真实零效应空对照通过完整流水线，并把其经验分辨率设为报告规则。
11. 在执行前绑定源码、分析器、硬件、预期记录数和证据哈希。
12. 保存失败的冻结实验，并且只在新锁下修复。

## 结论

GPU DSL 研究能够回答比速度竞赛更多的问题，但又不足以给出语言定理。它最强的
回答位于源码可表达性、硬件可行性、正确性和因素隔离的实现性能之间的边界。
当请求分母完整、失败阶段得到保留、每个实验处理只改变一个机制，并且测量下限由
实验证明而非主观假定时，这些回答才会真正有益于社区。

当前证据支持在 Ada 上给出这种形式的回答，但不支持宣称一个通用胜者。这一区分
不是修辞上的克制，而是最主要的科学结果。
