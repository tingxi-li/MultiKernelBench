## 2. The scientific results, read correctly

### 2.1 The 1.448× fused spread conflates realization with reachability

The 8 grid points both CUDA lanes lost (g05–g12: all BM128/BN256 and BM256/BN128
tiles) are precisely where both compiler winners live (tilelang g08, triton g05).
Cause: the shared fp32 epilogue staging tile needs 133,120–135,168 B against sm_89's
101,376 B opt-in cap. On the 11-point common-feasible subset the spread is ~**1.29×**
(tilelang 1.4730 @ g03, triton 1.4134 @ g00 vs CUDA 1.77–1.83); at the single shared
matched point (g01) it is 1.27×. So:

> **equal-budget gap (1.45×) = realization (~1.27–1.29×) + reachability (the rest).**

The reachability term is a *real DSL property* — the compiler lanes can occupy a tile
region the hand-written lanes' epilogue design cannot — but it is a different claim
from "same config, better code," and the ledger's disclosure of eligibility counts
never states that the excluded region coincides with the winning region. Related:
per-DSL minima are best-of-19 (TileLang) vs best-of-11 (CUDA) — unequal selection
intensity with no correction.

### 2.2 The unstated headline: the vendor fp16 anchor is now beaten

Phase 2 §2.3 concluded no custom lane beats precision-matched torch (torch:fp16 GBGS
cached = 1.523 ms). The new campaign is protocol-comparable (same hash-bound
runner/common/variants code, same shape/contract/dist/seed/warmup/GPU/torch build)
and its confirmed compiler-lane winners run **1.2897 / 1.2994 ms** — a 1.18× point
advantage, still ≥1.10× under the worst observed cross-campaign drift (the four g01
incumbent re-runs moved −5.7% to +0.06%). The quotable Phase-2 conclusion is very
likely overturned **at equal budget** — but no torch:fp16 lane ran in this campaign
(4 DSLs only, verified), so the claim is cross-campaign and uncertified. One
5-process torch:fp16 run inside a randomized session (~minutes, no build) closes it.
Neither the ledger nor any README mentions torch at all.

### 2.3 Confirmed narrative deltas for the top-level report

- **The single-number collapse must die.** Equal-budget post-transfer spread is now
  measured on two ops: matmul 1.31× (CI-separated endpoints), fused 1.448×
  (provisional; lane-min bootstrap 95% ≈ [1.37, 1.55]; common-subset ~1.29×). The
  collapse *thesis* is strengthened (7.0× native → ~1.3–1.45×); the constant is not.
  The old report's §9 bullet ("an equal-budget fused search was not run") is stale,
  and Phase 2 §1.1's FLOP-identity inheritance is now empirically falsified as a
  substitute (the fused equal-budget answer differs from matmul's).
- **The ~1.10× "TileLang compiler intrinsically better" residual does not
  generalize.** On the fused op, tilelang vs triton = 1.0075× (CIs overlap; bootstrap
  P(tilelang wins) = 0.68) — on TileLang's own home grid family. The residual is
  matmul-specific; the durable cross-op result is **compiler lanes vs hand lanes**
  (all 8 compiler cells' CIs sit fully below all 8 CUDA cells'; bootstrap P = 0).
- **Winner-curse hygiene held**: 16/16 confirmed estimates slower than screen
  (+0.8% to +5.5%), though the incumbent cells show ~2.2% of that is campaign drift,
  so `selection_bias_pct` mislabels drift as selection (~3× overstatement).
- **Fragility is honestly declared**: full four-way point order reproduces in only
  51% of bootstraps; within-DSL winners ~61% stable; every ordering call the
  campaign refused, it was right to refuse.

### 2.4 Gate results: what "passed" does and does not mean

- The fused kernels passing `semantic_mixed` means: within 1.25× of an **ideal
  fp16-contract implementation** on signed/zero-mean/Rademacher inputs. That is the
  right question for an fp16-contract benchmark, and it is a genuine advance over
  the old vacuous gate — but it is not "fp16 survives an fp32-tight gate." The fp32
  tier (`semantic_q32`, ~20–2000× tighter) has never been applied to any kernel.
- The accepted matmul v4 gate is so far a **false-positive-rate self-test**: its
  validation candidates are the same native implementations used as calibration
  anchors, and unlike fused v2 it has **no negative controls** — it has never been
  shown to reject a wrong kernel, and no real DSL kernel (no Phase-1 A/B/C/D recipe)
  has ever been adjudicated under it. "Does the 1.31× collapse survive a fair gate"
  remains open exactly as the ledger discloses; first contact happens inside the
  blocked reciprocal campaign (whose KC amendment ladder pre-acknowledges the donor
  recipe may fail).
- Thin margin worth watching: the tilelang fused winner's worst `row_sum_error_max`
  is 4.798e-7 vs a 5e-7 threshold — above anchor_max × 1.25 (4.538e-7), passing only
  via the frozen next-1-2-5 rounding step; ~1% of all validation rows (all four
  DSLs) are in the same position. Rule-clean, but anchor-to-kernel calibration
  transfer is imperfect on this metric and the 0/28,672 headline hides a 4% headroom.
- The v3→v4 remedy is direction-loaded by construction (more calibration seeds under
  a max-based rule can only loosen thresholds until validation passes). Mitigations
  are real (hashed prereg before calibration, rule-derived value, disjoint
  namespaces, anchor max exceeding the v3 failures) — but a second recalibration
  after a second failure would deserve skepticism; the acceptance is the second draw
  from a retry process.

## 3. Defects and gaps (ranked)

1. **[high] The historical reports are untouched.** Every P0 "text-only,
   near-zero-cost" fix from the prior review is still open: no document anywhere —
   old or new — discloses the LLM searcher (grep for opus/sonnet/LLM/searcher across
   the follow-up: zero hits), the CI-overlapping strict chains still stand verbatim
   in Phase 1/Phase 2/top-level, no per-op spread table exists, no native-tier
   lane/clock caveat was added. The follow-up fixes the future while the past keeps
   misleading its readers.
2. **[high, partly disclosed] Home-recipe anchoring persists in the new result.**
   The "equal" fused grid is byte-derived from the TileLang-discovered Phase-1
   family, and the only de-anchoring instrument (reciprocal transfer) has zero
   results behind 42/26 blockers. The 1.448× number inherits the anchoring critique
   in full.
3. **[medium] Feasibility/selection-intensity confound** (§2.1) — needs a stated
   decomposition (realization vs reachability) and a common-subset spread wherever
   1.448× is quoted.
4. **[medium] The vendor-anchor comparison is missing from the design** (§2.2) —
   the campaign's most consequential implication rests on a cross-campaign
   comparison with anchors that drifted up to 5.7%.
5. **[medium] Provenance bifurcation.** `fused_grid/results/` (312 MB — every
   executed screen/confirmation/robust record, both launch receipts, summary.json)
   is git-ignored, and the provenance snapshots hash 0 results files of 170 entries;
   the only committed anchor into the evidence is the handful of digests quoted in
   RUN_20260730.md. Meanwhile the whole tree landed as one post-hoc commit hours
   after execution, so freeze-before-validate ordering rests on self-written
   receipts and mtimes. (Contrast: all robust-gate raw JSONLs *are* committed.)
6. **[medium] Matmul v4 gate lacks negative controls and kernel contact** (§2.4).
7. **[medium] The performance estimand keeps the old distribution scope.** All 232
   timed records (152 + 80) use `dist=rand`, seed 0, legacy in-record gating; the
   signed-input robust gates ran only in separate correctness splits. Timing under
   torch.rand remains the benchmark's contract, but the scope should travel with the
   numbers.
8. **[low] Half-registered inference rule.** The estimator (`median_ci`) is
   hash-bound in the launch receipt, but `analyze_confirmation.py` — the
   strict-order/overlap decision logic — is absent from the receipt's source bundle
   and entered VCS post-run. As exercised the rule is maximally conservative
   (refuses every ordering), so the flexibility wasn't used; still, bind it next
   time.
9. **[low] n=5 was kept despite the prior review's power warning**, and predictably
   no within-DSL winner nor tilelang-vs-triton resolved; the tilelang winner's CI is
   driven by one −7% outlier process (point at the 79th percentile of its own
   interval). If ordering matters, n≈10–15 on the four contested cells; or report
   bootstrap CIs for the median.
10. **[low] Smaller items.** `overlapping_pairs=[[tilelang,triton]]` invites readers
    to think cuda_unlimited<cuda_noptx is resolved (lane-level bootstrap support is
    only 0.76); v5/v6 snapshots differ only in a README hash, unexplained in the
    ledger; snapshot capture misses GPU clock/persistence state and nvcc version
    (query failed, recorded); the ledger's convergence blocker list doesn't match
    `manifests/summary.json`; the convergence prereg has **no GPU-pinning field**
    and its "two models" are two same-family snapshots (gpt-5.6-sol/terra) — a weak
    searcher-diversity factor that also cannot retro-attribute the historical
    Opus/Sonnet claims; the post-hoc normalizer edited a validation evidence file
    (receipted, but a precedent worth avoiding); the cuda_unlimited silent-launch
    harness bug (unchecked `cudaFuncSetAttribute`) should be fixed in
    `fused_cuda_unlimited.py` — correctness screening was the only line of defense,
    and it caught a completely wrong kernel by 1.3% of elements on a near-vacuous
    budget.
